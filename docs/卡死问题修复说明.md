# 「又卡死了」问题排查与修复说明

日期：2026-11-18
涉及程序：`jarvis-desktop-v1.2\jarvis-desktop-v1`
改动备份：`_backup\portaudio-fix-before-20261118-2130\`

---

## 一、现象

使用者反馈"又卡死了"。现场状态：

- `jarvis-gui.log` 最后一行是 `[Web胶囊] 推送 LISTENING seq=3001`，之后再无任何 `[语音]` / `[直接执行] 听到` 输出
- 更早处出现 `Unclosed client session` 和 `Task was destroyed but it is pending!`（edge-tts 的异步流被掐断）
- 查询时已没有 `python` / `pythonw` 主进程，只剩 WebView2 残留进程
- Windows 事件日志里**没有** Application Error 记录

## 二、排查过程（含一个被实验推翻的假设）

### 假设 1：TTS 播报的 `pa.terminate()` 拆掉了全局 PortAudio

依据：`edge_speech.py` 和 `robot_voice.py` 每播报一次就 `PyAudio()` → `pa.terminate()`，
而 whisper 的常驻输入流挂在同一个 PortAudio 上，看起来"说完一句就听不见"完全对得上。

**实验证伪**：写了 `probe_portaudio.py` 做对照——旧写法（播报后 `terminate`）之后，输入流依然能正常读到音频块。
说明 PortAudio 的 `Pa_Initialize / Pa_Terminate` 是引用计数的，单次 terminate 并不会真的销毁全局状态。

所以这条**不是本次根因**。但"6 处各自建/毁 PortAudio"本身仍是隐患（一旦某条异常路径多调一次 terminate，
计数归零就会让所有流同时失效），因此作为加固保留了下来。

### 假设 2：日志"停在 LISTENING"= 卡死

**证伪**：`web_capsule.py` 的 `_tx_loop` **只在状态变化时**才打印 `[Web胶囊] 推送 …`。
状态不变就自然没有新日志。日志静止不等于程序卡死。

真正有信息量的是：修复前那一次，`LISTENING` 之后**再也没有 `[直接执行] 听到`** ——
也就是**播报结束后麦克风不再产出语音**。

### 定位到的确定性缺陷（4 条，均可独立造成"卡死"）

| # | 缺陷 | 位置 | 后果 |
|---|---|---|---|
| 1 | 麦克风读取失败被 `except: continue` 吞掉，无限空转 | `whisper_engine.listen_continuous` | 流失效后无日志、无自愈，界面永远停在 LISTENING（假活在） |
| 2 | `transcribe()` 被多个线程并发调用同一个模型 | `whisper_engine.transcribe` ↔ `confirm()→recognize_once` | ctranslate2 非线程安全，并发进 native 层 → 进程静默崩溃，无 traceback |
| 3 | 胶囊的 `evaluate_js` 是**裸调用**，没有超时看门狗 | `web_capsule._js_worker` | 页面/渲染进程一断，推送线程永久卡死；全屏 HUD 有看门狗，胶囊漏了 |
| 4 | Tk 的 `after` 链没有异常保护 | `jarvis_gui._render_tick / _poll_ui` | 回调抛一次异常 → 不再调度 → 界面永久冻结；胶囊子进程掉线也没有重启，界面直接消失 |

## 三、本次改动

### 新增模块

- **`audio_device.py`**：进程级 PortAudio 单例。只初始化一次、只在进程退出时释放，
  所有模块共用，各自只 `close` 自己的 stream。
- **`diagnostics.py`**：可观测性层。
  - `faulthandler.enable(...)` → native 崩溃写 `jarvis-crash.log`
  - `sys.excepthook` / `threading.excepthook` → 主线程与子线程的未捕获异常写 `jarvis-gui.log`
  - 心跳看门狗：Tk 主循环 / whisper 音频读取 / 胶囊子进程，任何一项长时间没动静就
    **把所有线程栈 dump 进日志**（30 秒冷却，避免刷屏）

### 修改点

| 文件 | 改动 |
|---|---|
| `whisper_engine.py` | 读取失败连续 8 次即重建输入流（自愈）；恢复不了就 `on_error` 上报并抛错，不再假装在听；`transcribe` 全局串行锁（锁包住整个惰性迭代过程）；新增 `last_heartbeat()` |
| `jarvis.py` | whisper 监听线程加了 `worker_dead` 信号，线程退出后**自动重启**，主循环不再空转；PortAudio 改用单例 |
| `web_capsule.py` | 补齐 `_push_js` 超时看门狗（8 秒，与全屏 HUD 对齐）；`_pending` 读写加锁 |
| `jarvis_gui.py` | 装上 diagnostics；`after` 链改为 `try/except/finally` 必定续上；日志队列限流 200 条/轮；**Web 胶囊子进程掉线自动重启，起不来则回退经典界面** |
| `edge_speech.py` / `robot_voice.py` | 改用 PortAudio 单例，播报结束只关自己的输出流 |

## 四、验证结果

1. **`probe_portaudio.py`**：新旧写法对照，输入流在播报后均存活 → 推翻了假设 1，也确认新写法没有引入回归。
2. **`probe_voice_chain.py`**（端到端）：whisper 常驻监听 + 一次播报动作后，
   心跳 `state=listening`、`距上次读数=0.15s`、`restarts=0` → **PASS**。
3. **冷启动冒烟（pythonw，与平时启动方式一致）**：

```
[Web胶囊] 推送 ACTING seq=448
[Web胶囊] 推送 LISTENING seq=1026          ← 播报结束回到监听
[直接执行] 听到: 这一次又新加了什么功能啊     ← 播报后立刻恢复识别（修复前此处彻底静止）
```

`jarvis-crash.log` 已创建且为 0 字节 → 期间无 native 崩溃。

## 五、以后再"卡死"怎么取证据

1. 先看 `jarvis-gui.log` 末尾有没有这段：

```
===== [看门狗] 检测到无响应：… =====
线程清单：
全部线程栈：
```

有的话，**卡在哪一行一眼就能看出来**（哪个线程停在哪个函数）。

2. 再看 `jarvis-crash.log`：非空说明是 native 崩溃（ctranslate2 / WebView2 / PortAudio），
   里面会有 C 层栈。

3. 两个文件都在程序目录下，直接发出来即可定位。

## 六、可调项

- `whisper_engine._MAX_READ_FAILS`（默认 8）：连续读失败多少次触发重建输入流
- `diagnostics._DUMP_COOLDOWN`（默认 30 秒）：两次线程栈 dump 的最小间隔
- `web_capsule._push_js` 的超时（默认 8 秒）：与全屏 HUD 保持一致
- Tk 心跳阈值（`jarvis_gui._watchdog_problems`，默认 5 秒）
